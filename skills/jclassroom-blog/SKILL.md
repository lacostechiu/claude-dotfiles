# 傑哥架站教室 Blog 撰寫 Skill

把傑哥的靈感、經驗、筆記，寫成一篇符合格式的 WordPress 部落格文章，儲存成 Markdown 檔，最後可以用 `publish_to_wp.py` 發佈到 jclassroom.net。

---

## 三大寫作鐵則（最重要）

開始寫之前先記住這三件事，違反任一條就要重寫：

1. **一般人看得懂** — 目標讀者是台灣中小企業主、剛接觸 WordPress 的個人品牌主，不是工程師。每個技術名詞第一次出現都要用一句話解釋。
2. **每段都要有具體例子** — 工具名、版本、操作步驟、實際數字、客戶案例，至少擇一。空泛原則沒人記得住。
3. **不要 AI 味、不要廢話** — 每段都要有實質資訊，過場句、修辭句、總結套話一律刪掉。每段 3-5 句為原則。

---

## 第一步：釐清文章素材

動筆前先確認：

1. **主題是什麼？** 一個具體的 WordPress、架站、SEO 或自動化主題
2. **目標讀者是誰？** 預設是台灣中小企業主、個人品牌主、初中階 WordPress 用戶
3. **有哪些重點段落？** 預計幾個 H2 小節？每節核心內容？
4. **有沒有可引用的實際案例或工具？** 外掛名稱、客戶情境、實測數字
5. **SEO 關鍵字是什麼？** 這篇文章希望被 Google 搜尋到的詞

如果使用者沒給足夠資訊，用 `AskUserQuestion` 工具逐一詢問，**不要自行腦補技術細節**（例如不要憑空說某個外掛叫什麼名字、價格多少）。

## 第二步：產出 Markdown 檔案

### 標題撰寫原則（最關鍵）

文章標題決定 SEO 表現與點擊率，務必**具體描述 + 包含關鍵字**。寫之前先想：讀者會用哪些字 Google 搜尋這篇？把那些字塞進標題。

**推薦格式**：

| 格式 | 範例 |
|------|------|
| `主題：具體做法（含工具）` | AI 自動寫 SEO 報告工作流：運用 MCP 接上數據產出工作報告 |
| `行動 + 工具/外掛 + 結果` | 用 WPvivid 把 WordPress 從本機搬到正式站，5 步驟搞定 |
| `問題 + 解法/答案` | WordPress 後台變慢怎麼辦？三個設定立刻改善 |
| `對象 + 主題 + 強化詞` | 中小企業主必看：WordPress 安全性設定完整指南 |

**好標題的 4 個條件**：

1. **具體**：講出文章實際在做什麼，不要「分享心得」「使用體驗」這種空話
2. **含關鍵字**：把讀者會 Google 的詞放進去（外掛名、工具名、平台名、操作動詞）
3. **長度合宜**：中文 20–35 字，過短沒資訊量、過長搜尋結果會被截斷
4. **明確標的物**：點進來能拿到什麼（教學、評測、流程、案例）

**好標題（示範）**：
- ✅「AI 自動寫 SEO 報告工作流：運用 MCP 接上數據產出工作報告」— 含 AI、SEO 報告、工作流、MCP 四個關鍵字
- ✅「Obsidian 的設定與外掛一鍵發佈 WordPress 文章」— 含 Obsidian、外掛、WordPress、發佈
- ✅「在 Runcloud 開啟 Redis Cache 加速 WordPress 後台」— 主機、外掛、操作、結果都有

**壞標題（要重寫）**：
- ❌「我的 AI 使用心得」— 空泛，無關鍵字
- ❌「關於 WordPress 的一些想法」— 沒主題、沒關鍵字
- ❌「分享一個小技巧」— 完全無資訊
- ❌「淺談 SEO」— 主題太大，沒講做什麼
- ❌「讓你的網站起飛」— 行銷話術，無關鍵字

**標題與 slug 的對應**：
- 標題定下來之後，slug 從標題的英文關鍵字組合
- 範例：標題「運用 MCP 接上數據產出工作報告」→ slug `mcp-ai-seo-report`

---

### YAML Frontmatter 格式

新文章（草稿）使用以下格式，**不加 wp_id 和 featured_media**：

```yaml
---
title: "主題：具體做法（含關鍵字）"
slug: english-slug-with-hyphens
categories: [WordPress教學]
tags: [標籤1, 標籤2, 標籤3]
status: draft
description: "80–150 字 SEO meta description，包含主要關鍵字，說明讀者能拿到什麼"
---
```

**slug 規則：**
- 全小寫英文，單字之間用 `-` 連接
- 對應文章主題的英文翻譯，例如：`wordpress-security-tips`
- 避免超過 20 個英文字，太長就截取重點
- 不含中文、特殊符號

**categories 常用選項：**
- `WordPress教學`、`WordPress外掛`、`WordPress主機`、`SEO`、`自動化工具`、`架站教學`

**description 撰寫原則：**
- 控制在 80–150 字（實際偏短較自然，例如 90 字左右）
- 包含主要關鍵字
- 說明讀者的痛點 + 文章提供的解法（兩段式）
- 不要以「本文」「本篇」開頭

**範例**：
> 客戶看 Google Analytics 總是頭痛——專有名詞看不懂、數據不知道怎麼解讀。傑哥用 Claude AI 接到 GA4 與 Search Console，讓 AI 直接讀 Google 的數據，產出客戶看得懂的報告書。

這個範例先點出客戶痛點（看不懂 GA），再說明傑哥的解法（AI + MCP），關鍵字 Claude AI、GA4、Search Console、MCP 都自然帶到。

---

### 文章結構

#### 第一段：開場摘要（必要）

第一段不加標題，直接放在 frontmatter 後面。長度約 50–80 字（2-4 句）。

**寫法**（擇一）：
- **背景交代**：說明這個主題為什麼重要、用什麼情境
- **親身經驗引入**：「傑哥使用 VPS 主機已經有 6 年的時間…」
- **問題鋪陳**：讀者會遇到什麼狀況

**真實範例（取自舊文）：**

> WordPress 網站安全一直是重要課題。因為其使用率占所有網站的 4 成，很容易成為駭客和惡意軟體覬覦的對象。

> 傑哥使用 VPS 主機已經有 6 年的時間，期間從自行摸索，到使用專業的平台 Runcloud 管理。

**禁用開場：**
- ❌「隨著數位轉型的趨勢…」
- ❌「在這個 WordPress 越來越普及的時代…」
- ❌「眾所周知，網站安全是…」

---

#### 主體段落：H2 為主，H3 補充

每個重點用 H2 標題（`##`）獨立一節：

```markdown
## WordPress 網站備份

內容說明...

## 選擇具有高安全性的主機

內容說明...
```

**標題規則：**
- **陳述句為主**，必要時可用疑問句帶出問題（「MCP 是什麼？簡單說就是 AI 的 USB 接頭」）
- **塞入關鍵字、術語、工具名**，讓讀者掃一眼就知道這節有沒有他要的資訊
- 不用編號、不寫「第一點」「首先」「重點一」
- 善用「術語：白話解釋」格式：「進步機會關鍵字：最有機會贏得排名的潛力關鍵字」
- 直接命名這節在做什麼：「加強讀寫權限」「定期備份策略」「安裝 Google 分析和網站管理工具的二個 MCP」

**段落內容規則：**
- **每段 3-5 句**，控制資訊密度
- **以散文敘述為主**，不要每段都列 bullet
- bullet list 只用於：技術操作步驟、工具規格比較、明確的條件清單
- 每節 150–400 字
- **必須出現至少一個具體例子**：工具名、版本、客戶情境、實測數字

**子標題（H3）使用時機：**
- 一個 H2 章節下有 2-3 個並列的小重點時才用
- 範例：「## 寄信工具」下面可分「### YaySMTP 設定步驟」「### 為什麼不推薦預設 PHP mail」

---

#### 結尾段落

**不要寫公式化總結**（例如「整理一下這篇提到的三個重點：1...2...3...」）。

**改用以下兩種真實風格擇一**：

**A. 陳述式總結**（取自舊文）：

> 以上 5 個步驟是傑哥在執行網站遷移的程序，連續使用 10 次以上，都會成功的方法。

> 展望未來，AI 將會愈來愈強大，網頁設計師需要學會駕馭它，而不是被取代。

**B. 邀請互動**（取自舊文）：

> 若還有其他問題，歡迎寄信或留言給我。

> 也歡迎在留言區分享你的經驗。

**禁用結尾：**
- ❌「希望本文對您有幫助」
- ❌「讓我們拭目以待」
- ❌「相信透過不斷的努力，我們一定能…」
- ❌「攜手共進，未來可期」

## 第三步：儲存檔案

### 三段式資料夾流程

| 階段 | 資料夾 | 用途 |
|-----|--------|------|
| 修改中 | `WordPress/02-Process/` | Claude 產出的草稿存這裡，人工審閱與加工 |
| 已完成 | `WordPress/03-Output/` | 改好定稿，準備發佈 |

**新草稿一律存到 `WordPress/02-Process/`**，等使用者修改完成才會手動移到 `03-Output/`。

完整路徑：`D:\GoogleDrive\Execution\Valut-Wordpress\WordPress\02-Process\`

**檔名格式**：`YYYY-MM-DD-slug.md`

**範例**：`2026-04-09-wordpress-security-tips.md`

確認日期用 `date` 指令取得台北時間（UTC+8）。

## 傑哥的真實寫作風格

以下歸納自實際舊文的觀察，動筆時務必對照。

### 1. 第三人稱「傑哥」是招牌

每篇文章**至少出現 2 次以上**「傑哥」第三人稱。常見用法：

- 開場引入經驗：「傑哥使用 VPS 主機已經有 6 年的時間…」
- 推薦工具：「傑哥推薦 WPvivid，因為…」
- 提供觀點：「傑哥認為…」「以傑哥的經驗…」
- 結尾提建議：「傑哥的建議是先做備份再升級。」

「我」「我們」用得少，「你」用在直接給讀者操作指示時（「你可以在這裡點擊…」）。

### 2. 舉例必須具體到「能照做」

**寫得出來的具體**（這樣才及格）：
- ✅「使用 Gandi 時，更改 DNS 的資料，幾乎幾分鐘就生效了」
- ✅「Runcloud 一個月 4 塊錢台幣的備份方案」
- ✅「設定快捷鍵 Ctrl+Shift+O 直接執行發布」
- ✅「網站從 8 秒降到 2 秒」

**含糊到沒用**（這樣要重寫）：
- ❌「設定後會明顯變快」
- ❌「市面上有許多工具可以選擇」
- ❌「這個方法效果很好」

**不要假設情境**（除非真的找不到例子）：
- ⚠️「假設你有一個電商網站…」 — 改成真實客戶情境會更有力

### 3. 一般人看得懂：技術名詞要解釋

第一次出現的技術名詞，用一句話解釋。

**範例：**
- ✅「VPS（Virtual Private Server，虛擬專屬主機）就像一塊只有你能用的伺服器空間。」
- ✅「DNS（網域名稱系統）就是把網址翻譯成 IP 位址的查號台。」
- ❌ 直接寫「VPS 的設定」就接下去 — 中小企業主看不懂

但**不要每個詞都解釋**，否則變成國中課本。判斷標準：第一段中出現的核心概念解釋；之後重複出現就不用了。

### 4. 段落結構：散文為主，bullet 為輔

**用散文的時機**（90% 的段落）：
- 解釋原因、講概念、敘述經驗、做比較

**用 bullet list 的時機**（10% 的段落）：
- 操作步驟（1, 2, 3）
- 規格條列（外掛功能清單）
- 對比清單（A 主機 vs B 主機）

連續 3 個段落都是 bullet list 就要改，讀起來會像產品文件。

### 5. 段落間的銜接

不要靠「此外」「另外」「再者」這些連接詞。讓段落自然銜接：

**用因果關係**：「因為這樣，所以…」「這樣設定的結果是…」
**用實例延伸**：「傑哥之前碰過一個客戶…」
**用時序**：「設定完之後，下一步是…」

### 6. 語氣校準

| 太正式（不要） | 適當（傑哥風） | 太隨便（不要） |
|--------|------|--------|
| 予以高度重視 | 這件事要特別注意 | 超在意的 |
| 經由詳細的調查分析 | 排查之後發現 | 隨便 google 一下 |
| 此舉將有效提升系統效能 | 這個做法能改善網站速度 | 改完之後快超多 |
| 鑑於上述情況 | 因為這個原因 | 反正就是這樣 |
| 進行深入的探討 | 深入討論 | 來聊一下 |

## 反 AI 味檢查（19 項）

寫完後對照以下清單。任何一項出現都要改。

### 開場與連接詞（最常見）

**1. 時代開場白** — 直接刪除：
「隨著…的發展」「在…的背景下」「在這個…的時代」「當今時代」

**2. 共識開場白** — 刪除：
「眾所周知」「不言而喻」「顯而易見」「毋庸置疑」「不可否認」

**3. 連接詞濫用** — 大量刪減：
- 遞進：「此外」「另外」「不僅如此」「除此之外」
- 列舉：「首先…其次…再次…最後」
- 總結：「總的來說」「總而言之」「綜上所述」

### 互聯網黑話（職場術語）

| 避免 | 改用 |
|------|------|
| 賦能 | 幫助、支援 |
| 痛點 | 問題、困難 |
| 閉環 | 完整流程 |
| 沉澱 | 累積、整理 |
| 深耕 | 專注、長期投入 |
| 彰顯 | 顯示、表現 |
| 標誌著 | 代表 |
| 擁抱 | 接受、採用 |
| 賽道 | 領域 |

### 翻譯腔

**「這是一個…的事情」** → 直接「這很重要」

**「的」字堆疊**：連續超過兩個「的」就要重寫。
- 改寫前：這是我們公司的產品設計部門的資深設計師的最新的作品。
- 改寫後：這是我們設計部資深設計師的新作品。

**被動語態**：「這個問題被認為是」→「大家認為這個問題是」

### 書面語過重

| 避免 | 改用 |
|------|------|
| 其 | 它的、他的 |
| 該 | 這個、那個 |
| 此 | 這、這個 |
| 予以 | 給、進行 |
| 鑑於…的情況 | 因為… |
| 基於…的考量 | 考慮到… |

### 結構與節奏

- **打破「三點公式」**：不要每篇都是「總結開場 + 三點展開 + 金句結尾」
- **否定式排比**：「不僅 X，更是 Y」 → 直接說 Y
- **句子長度單一**：連續三句以上相同長度就要調整
- **絕對詞**：「總是」→「通常」；「每個人都」→「大部分人」

### 結尾套話（禁用）

「讓我們拭目以待」「未來可期」「攜手共進」「相信在…的努力下」「這值得我們深思」「也許這就是…的意義」「希望本文對您有幫助」

## 發佈方式

文章完稿並從 `02-Process/` 移到 `03-Output/` 後，用以下指令上傳：

```bash
wp-publish "WordPress/03-Output/YYYY-MM-DD-slug.md"
```

或直接呼叫 Python 腳本：

```bash
python publish_to_wp.py "WordPress/03-Output/YYYY-MM-DD-slug.md"
```

上傳成功後 WordPress 會回傳 Post ID，用 `wp-get [Post_ID]` 把 `wp_id` 寫回 frontmatter，之後修改可直接更新同一篇。
