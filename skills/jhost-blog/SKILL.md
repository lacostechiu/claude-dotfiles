# jhost-blog: jhost.tw 部落格寫作 Skill

把 Jhost 系統的功能、客戶案例、踩坑經驗、產品更新，寫成一篇 SaaS 推廣風格的部落格文章，產出可直接貼到 Jhost editor 發佈的 Markdown 檔。

---

## 命名慣例（必讀）

**品牌名統一寫 `Jhost`（首字大寫）**——這是對外正式品牌名，所有正文、標題、description、H2、敘述句都要用 `Jhost`。

**例外保留小寫 `jhost`** 的場景（這些是技術識別字，不是品牌名）：

- 網域與 URL：`jhost.tw`、`editor.jhost.tw`、`https://editor.jhost.tw/apply/`、`https://editor.jhost.tw/jhost/`
- 檔名 / 資料夾 / repo 名：`jhost-blog`、`jhost-copy/`、code block 內的路徑
- 程式碼識別字：YAML key、變數名、API endpoint
- 引用過去文章標題或 commit message 內已寫成小寫 `jhost` 的字串（保留原貌）

判斷原則：人讀的「這個產品的名字」→ `Jhost`；機器讀的「這個字串」→ `jhost`。

---

## 三大寫作鐵則

開始前先記住這三件事，違反任一條就要重寫：

1. **目標讀者是「正在考慮架站的中小企業主」** — 不是工程師、不是 jhost 內部團隊。讀者可能正在用 WordPress 想搬家、可能是新創想開官網、可能是被代理商收費收怕了想自架。每個技術名詞第一次出現都要用一句話翻譯成「為什麼這對我有意義」。
2. **重事實、輕推銷** — 用實際數字、客戶案例、技術細節說服，不用「最棒」「業界唯一」這種空話。SaaS 推廣文的轉化率取決於「可信度」而非「氣勢」。
3. **不要 AI 味、不要廢話** — 每段 3-5 句、每段都有具體資訊（工具名、數字、案例、操作）。過場句、修辭句、總結套話一律刪掉。

## 第一步：釐清文章素材

動筆前先確認：

1. **文章類型是哪一種？**（影響結構與口吻）
   - **系統介紹**：解釋 jhost 是什麼、跟 WordPress / Wix / Shopify 差在哪
   - **客戶案例**：具名某個客戶從 0 到上線、解決了什麼問題、達到什麼結果
   - **功能說明**：某個 jhost 獨家功能（AI 寫作、AI 標題優化、自動 SEO 等）的深入介紹
   - **比較文**：jhost vs WordPress / jhost vs Wix / Astro vs WordPress 的客觀對比
   - **踩坑紀實**：開發 jhost 或上線客戶遇到的技術卡點，寫成有教育意義的故事
   - **趨勢觀察**：靜態網站、SaaS 架站、AI 寫作對行銷的影響等
2. **這篇要怎麼幫到讀者下決定？** 是讓他「想試試 jhost」、「想了解 Astro」、還是「想跟傑哥討論搬家」？要明確。
3. **有哪些可引用的真實素材？** 客戶名稱、實際數字（流量、速度、上線時間）、截圖、技術細節
4. **SEO 關鍵字是什麼？** 中小企業主會 Google 哪些字找到這篇？（例：「WordPress 替代方案」「Astro 架站」「SaaS 架站系統推薦」「自動建站」）

如果使用者沒給足夠資訊，用 `AskUserQuestion` 工具逐一詢問。**不要憑空幫客戶捏造數字、沒發生的功能、未確認的價格**。

## 第二步：產出 Markdown 檔案

### 標題撰寫原則

文章標題決定 SEO 排名與 CTR，務必**具體 + 含關鍵字**。寫之前先想：讀者用哪幾個字會 Google 搜尋這篇？把那幾個字塞進去。

**推薦格式**：

| 格式 | 範例 |
|------|------|
| `主題：具體做法（含工具）` | 用 Astro 取代 WordPress 的三個理由：速度、成本、安全 |
| `案例 + 結果` | 硬翰科技從 WordPress 搬到 jhost：上線速度 8 倍，月流量穩定成長 |
| `對象 + 主題 + 強化詞` | 中小企業主必看：什麼情況下 jhost 比 WordPress 划算？ |
| `數字 + 主題` | 30 秒自動建站：jhost 怎麼把 WordPress 一週流程壓到一杯咖啡時間 |
| `比較 + 結論` | jhost vs WordPress：六個面向比給你看，哪邊適合你 |

**好標題的 4 個條件**：
1. **具體**：講清楚這篇講什麼，不要「淺談 SaaS 架站」這種空話
2. **含關鍵字**：把讀者會 Google 的字塞進去（jhost、Astro、WordPress、AI 寫作、SaaS 架站、自動建站、Cloudflare Pages）
3. **長度**：中文 20–35 字
4. **明確收穫**：點進來能拿到什麼（理由、案例、流程、比較表）

**好標題（示範）**：
- ✅「自己做的架站系統 jhost：用 Astro 加 AI 寫作，硬翰是第一個上線客戶」— 含 jhost、Astro、AI 寫作、客戶名
- ✅「為什麼 Astro 比 WordPress 快 5 倍？三個技術原因 + 中小企業實測」— 含 Astro、WordPress、技術原因、實測
- ✅「jhost 的 AI 標題優化怎麼用：給標題跟內文，3 分鐘優化整篇 SEO」— 含 jhost、AI 標題優化、SEO

**壞標題（要重寫）**：
- ❌「淺談 SaaS 架站」— 空泛，無關鍵字
- ❌「我們的架站新時代」— 無資訊、像新聞稿
- ❌「為什麼選 jhost？」— 像 FAQ，不像文章標題
- ❌「讓你的網站起飛」— 行銷話術
- ❌「從 0 到 1 打造你的網站」— 太常見，沒辨識度

### YAML Frontmatter 格式（符合 jhost content schema）

文章用 YAML frontmatter 開頭，欄位**完全對應 jhost 的 post collection schema**，未來如果做 CLI 發佈（類似 WordPress 的 wp-publish.py）可直接讀取，現在則由使用者人工從這裡複製值貼到 editor 欄位。

```yaml
---
title: "自己做的架站系統 jhost：用 Astro 加 AI 寫作，硬翰是第一個上線客戶"
description: "傑哥用 Astro 開發了一套 SaaS 架站系統 jhost。客戶選版型、填基本資料、審核通過後自動上線，後台融合 WordPress 體驗加上 AI 寫文章與 SEO 標題。第一個客戶硬翰已上線，分享開發過程踩到的真實卡點。"
publishedAt: 2026-05-08
draft: true
category: 客戶案例
cover: ""
---

傑哥研發了大半年的架站系統 jhost...

## H2 標題

...
```

**欄位說明**（對應 `api-server/templates/_default/src/content/config.ts` 的 posts schema）：

| 欄位 | 類型 | 必填 | 說明 |
|------|------|-----|------|
| `title` | string | ✅ | 文章標題，20–35 字，含關鍵字 |
| `description` | string | 建議寫 | Meta Description，80–150 字，痛點+解法兩段式 |
| `publishedAt` | date | 建議寫 | YYYY-MM-DD 格式，今天的台北日期 |
| `draft` | boolean | ✅ | 預設 `true`（草稿），使用者最終發佈時 editor 會自動切 false |
| `category` | string \| string[] | 建議寫 | 從下面分類擇一（單選用 string，多選用 array） |
| `cover` | string | 選填 | 封面圖 URL，可留空字串，後續在 editor 內上傳 |
| `ogImage` | string | 選填 | OG 分享圖，通常與 cover 相同，留空即可 |

**category 常用選項**（jhost.tw 官網部落格用）：
- `系統介紹`：解釋 jhost 是什麼、特色、定位
- `客戶案例`：具名客戶 + 結果
- `功能說明`：單一功能深入講
- `WordPress 比較`：對比文
- `教學`：使用 jhost 的步驟、技巧
- `趨勢觀察`：產業趨勢、SaaS / Astro 普及度
- `踩坑紀實`：開發或運維踩到的技術卡點

**title 寫法注意**：含冒號或特殊字元（：、—、等）時，整個 title 用雙引號包起來，避免 YAML parse 錯誤。

**publishedAt 寫法**：YYYY-MM-DD 不加引號（YAML 會自動解析成日期）。確認日期用 `date` 指令取得台北時間（UTC+8）。

### 文章結構（正文部分）

#### 第一段：開場摘要（必要）

第一段不加標題，緊接在分隔線之後。長度 50–80 字（2-4 句）。

**寫法**（擇一）：
- **客戶情境引入**：「硬翰科技 27 年的電焊機老牌廠商...」
- **問題鋪陳**：「WordPress 用了五年，每月維護費又漲了。換還不換？」
- **數據開場**：「jhost 上線一個禮拜，第一個客戶月流量穩定成長 12%。」
- **直接揭示**：「傑哥研發了大半年的架站系統 jhost，這個禮拜終於把第一個客戶推上線。」

**禁用開場**：
- ❌「隨著 SaaS 普及的趨勢...」
- ❌「在這個 AI 改變一切的時代...」
- ❌「眾所周知，網站速度很重要...」

---

#### 主體段落：H2 為主，H3 補充

每個重點用 H2 標題（`##`）獨立一節：

```markdown
## jhost 是什麼？選版型、填表、自動上線一條龍

內容說明...

## 後台融合 WordPress：AI 自動完成 SEO、AI 寫文章草稿

內容說明...
```

**H2 標題規則**：
- **陳述句為主**，必要時可用疑問句帶出問題（「為什麼 Astro 比 WordPress 快？」）
- **塞入關鍵字、術語、工具名**，掃一眼就知道這節在講什麼
- 不用編號、不寫「第一點」「首先」「重點一」
- 直接命名這節在做什麼：「自動建站流程詳解」「客戶踩到的四個卡點」「跟 WordPress 的核心差異」

**段落內容規則**：
- **每段 3-5 句**，控制資訊密度
- **以散文敘述為主**，不要每段都列 bullet
- bullet list 只用於：技術操作步驟、規格比較、明確的條件清單
- 每節 150–400 字
- **每節必須有至少一個具體例子**：客戶名、版本號、實測數字、操作步驟

**子標題（H3）使用時機**：
- 一個 H2 章節下有 2-3 個並列的小重點時才用
- 範例：「## 開發過程踩到的四個卡點」下面分「### 卡點 1：VPS 跟 GitHub 不同步」「### 卡點 2：Cloudflare Pages 沒 404 會跳首頁」

---

#### 結尾段落

**不要寫公式化總結**（例如「整理一下這篇提到的三個重點：1...2...3...」）。

**改用以下三種真實風格擇一**：

**A. 下一步陳述 + 邀請**（推薦給 SaaS 推廣文）：

> 第一個客戶上線完成，明天計畫再開第二個網站，把流程再走一遍。如果你也是 WordPress 用了多年想找替代方案的中小企業主，歡迎留言或寄信給傑哥討論。

**B. 落地建議**：

> 傑哥的建議是先別急著搬家。先去 jhost.tw 看一下版型有沒有合用的，再評估遷移成本。

**C. 適用情境清單**：

> 什麼樣的網站適合 jhost：產品官網、形象網站、診所/事務所、品牌部落格。什麼樣的網站不適合：電商（要會員 + 金流）、論壇、需要複雜會員權限的平台。

**禁用結尾**：
- ❌「希望本文對您有幫助」
- ❌「讓我們拭目以待」
- ❌「相信透過不斷的努力...」
- ❌「歡迎了解更多」（接 CTA 連結也不行，太業配）
- ❌「現在就試試 jhost！」（直接喊話太銷售）

## jhost 的寫作風格（與 jclassroom 不同）

### 1. 第三人稱「傑哥」是同一個人，但語境不同

jhost.tw 的「傑哥」是**產品開發者 / 創辦人**身份，不是教學者。常見用法：

- 開發背景：「傑哥研發了大半年的架站系統...」
- 設計理念：「傑哥當初設計 jhost 時，就決定不走 WordPress 那條路，因為...」
- 客戶服務：「傑哥審核通過按一個按鈕後，系統會自動跑完九個步驟...」
- 觀點表達：「傑哥認為 SaaS 架站的關鍵不是版型多寡，而是...」

**避免「教學語氣」**：
- ❌「傑哥來教大家怎麼用 jhost」（這是 jclassroom 的口吻）
- ✅「傑哥分享 jhost 的設計思路，跟硬翰上線過程踩到的卡點」

### 2. 數字 + 案例是 SaaS 推廣的根

每篇至少要有 3 處具體數字 / 案例：

- ✅「30-60 秒內自動跑完九個步驟」
- ✅「硬翰每月 100 點擊，30% 流量點到 404」
- ✅「800、1500、3000 token 三種 AI 文章長度」
- ✅「10 個版型內建：診所、餐廳、律師...」
- ❌「速度很快」「省了很多時間」「客戶滿意」

### 3. 跟 WordPress 對比要客觀，不能踩

WordPress 是讀者熟悉的參考點，**對比是合理的，但不能變成踩 WP**：

- ✅「WordPress 全球 4 成網站在用，後台習慣是強項。jhost 保留這些習慣，多了 AI 寫作。」
- ✅「WordPress 用 Redirection 外掛做轉址要打到主機。Cloudflare Pages 在邊緣節點直接攔截，更快。」
- ❌「WordPress 太慢、太複雜、太不安全」（情緒化）
- ❌「不要再用 WordPress 了！」（攻擊性）

讀者很多是 WP 重度使用者，踩 WP 會直接讓他們關掉文章。

### 4. 技術名詞要翻譯成「對讀者的意義」

第一次出現的技術名詞，用一句話解釋 + 為什麼重要：

- ✅「Cloudflare Pages（一個免費的靜態網站託管平台，全球 CDN 速度很快）」
- ✅「VPS（Virtual Private Server，虛擬專屬主機，可以想成只有你能用的雲端電腦）」
- ✅「Astro 是近兩年很紅的網站框架，特色是輸出靜態 HTML，速度比 WordPress 快很多倍」
- ❌ 直接寫「Astro 的 SSG 模式」（沒解釋）
- ❌ 直接寫「我們用 git pull --rebase --autostash」（指令直接丟）

但**不是每個詞都要解釋**。判斷標準：
- 中小企業主聽不懂的，要解釋
- 已解釋過的，後文不重複

### 5. 段落結構：散文 + 少量 bullet

**用散文的時機**（90% 的段落）：
- 解釋功能、講設計思路、敘述客戶情境、做對比

**用 bullet 的時機**（10% 的段落）：
- 流程步驟（1, 2, 3）
- 規格清單（10 個版型列表）
- 對比清單（適合 / 不適合的網站類型）

## 反 AI 味檢查（19 項）

寫完後對照以下清單。任何一項出現都要改。

### 開場與連接詞

**1. 時代開場白** — 直接刪：「隨著…的發展」「在…的背景下」「在這個…的時代」

**2. 共識開場白** — 刪：「眾所周知」「不言而喻」「顯而易見」「毋庸置疑」「不可否認」

**3. 連接詞濫用** — 大量刪減：「此外」「另外」「不僅如此」「除此之外」「首先…其次…再次…最後」「總的來說」「總而言之」「綜上所述」

### 互聯網黑話 / 職場術語

| 避免 | 改用 |
|------|------|
| 賦能 | 幫助、支援 |
| 痛點 | 問題、困難 |
| 閉環 | 完整流程 |
| 沉澱 | 累積、整理 |
| 深耕 | 專注、長期投入 |
| 彰顯 | 顯示、表現 |
| 標誌著 | 代表 |
| 擁抱 | 接受、採用 |
| 賽道 | 領域 |
| 對齊 | 確認方向一致 |

### SaaS 推廣常見地雷詞（額外注意）

| 避免 | 改用 |
|------|------|
| 一鍵搞定 | 按一個按鈕完成 |
| 業界唯一 | 目前 WordPress 外掛市場找不到 |
| 顛覆傳統 | 跟 WordPress 不同的做法是 |
| 革命性 | 新的 |
| 強大的 | 直接講功能就好 |
| 完美的 | 直接講優點就好 |
| 領先業界 | 領先了什麼？要具體 |

### 翻譯腔 / 書面語

- 「這是一個...的事情」 → 直接「這很重要」
- 連續超過兩個「的」就要重寫
- 「被認為是」 → 「大家認為」
- 「予以」「該」「此」「其」 → 改口語

### 結構與節奏

- **打破「三點公式」**：不要每篇都是「總結開場 + 三點展開 + 金句結尾」
- **否定式排比**：「不僅 X，更是 Y」 → 直接說 Y
- **句子長度單一**：連續三句以上相同長度就要調整
- **絕對詞**：「總是」→「通常」；「每個」→「大部分」

### 結尾套話（禁用）

「讓我們拭目以待」「未來可期」「攜手共進」「這值得我們深思」「也許這就是…的意義」「希望本文對您有幫助」「現在就試試 jhost！」

## 發佈到 jhost editor 的流程（人工複製貼上）

文章寫完之後的發佈流程：

1. 開檔案 `D:\GoogleDrive\Execution\Valut-Wordpress\Astro\YYYY-MM-DD-slug.md`
2. 開啟 jhost editor 對應 client（例：`https://editor.jhost.tw/jhost/`）
3. 按「新增文章」
4. 從 YAML frontmatter 複製對應值：
   - `title` 的值 → 貼到 editor 的 **Title 欄位**
   - `description` 的值 → 貼到 editor 的 **Description 欄位**（或留空，按「AI 自動完成 SEO」由 AI 生成）
   - `category` 的值 → 貼到 editor 的 **Category 欄位**
   - `publishedAt` 的值 → 貼到 editor 的 **發佈日期欄位**
5. 選取 frontmatter（`---` 之後）下方的全部正文 → 貼到 editor 的 **Markdown body 編輯區**
6. 在 editor 內可選用：
   - 「AI 自動完成 SEO」自動補/優化 title + description
   - 「AI 標題優化」給每個 H2 三個替代版本，挑喜歡的採用
   - 上傳封面圖（若 `cover` 欄位是 URL，可直接填入；若留空就在 editor 裡上傳）
7. 確認無誤、把 `draft` 切換為 `false`（或用 editor 的「發佈」按鈕），jhost 會自動 commit/push/build/deploy 到 jhost.tw

## 未來自動化路線（保留 YAML 的原因）

目前 **沒有** CLI 發佈腳本，所以是人工複製貼上。但 YAML frontmatter 完全對應 jhost 的 post collection schema，未來如果做以下任一自動化都不用改格式：

1. **CLI publisher**（類似 WordPress 的 `wp-publish.py`）：腳本讀 YAML、呼叫 jhost API 建立 post
2. **Obsidian → VPS 直推**：plugin 把 .md 檔丟到 client 的 GitHub repo + 觸發 republish
3. **批次匯入**：把 `Astro/` 資料夾整批匯入 jhost editor

決定要做自動化時，YAML 已經就位，省一步轉檔。

**單篇發佈仍建議走 editor**：editor 內的 AI 工具（標題優化、SEO 自動完成、文章草稿）是 jhost 最大的差異化武器，跳過很可惜。
